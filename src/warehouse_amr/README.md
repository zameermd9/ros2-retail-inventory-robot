# Warehouse AMR — custom URDF, camera and LiDAR

Target: Ubuntu 24.04, ROS 2 Jazzy, Gazebo Harmonic. Package: `warehouse_amr`.

This is a custom simulated industrial-style differential-drive robot. It is not
a calibrated digital twin of a commercial product. The multi-part URDF visuals
include a chassis, metal cover, payload deck, bumpers, side panels, vents, wheel
hubs, lights, camera mast and roof scanner. Collision shapes, masses and inertias
are specified for the physical links. Camera imagery and laser returns are
generated by Gazebo's sensor system; they are not prerecorded or synthetic ROS
publishers. The camera is an RGB camera, not a stereo/depth camera, despite the
multi-lens-style housing.

## Contents and scope

- `urdf/warehouse_amr.urdf`: editable plain URDF; includes Gazebo Harmonic extensions.
- `worlds/warehouse.sdf`: shelves, totes, lane markings, obstacle crate, visual dock.
- `launch/sim.launch.py`: Gazebo, robot spawn, robot_state_publisher, bridge,
  command watchdog and RViz.
- `config/bridge.yaml`: camera, calibration, LiDAR, wheel joints, odometry, TF,
  simulation clock and velocity command mappings.
- `rviz/warehouse.rviz`: robot, laser overlay and camera image panel.
- `scripts/verify_runtime.py`: live data and transform validation.
- `scripts/cmd_watchdog.py`: limits command speeds and stops on a 0.5-second
  command timeout. This is a simulation convenience, not a safety controller.

This release is the robot-and-sensors foundation. Nav2, mapping, tag recognition,
battery modelling and autonomous docking are not implemented yet. The dock in
the scene is geometry only. Robot lights are visual details, not status logic.

## 1. Install dependencies

Close the old Gazebo demo and stop the old bridge with Ctrl+C first. Run in Ubuntu:

```bash
source /opt/ros/jazzy/setup.bash
sudo apt update
sudo apt install ros-jazzy-ros-gz ros-jazzy-robot-state-publisher ros-jazzy-rviz2 ros-jazzy-tf2-ros ros-jazzy-rclpy python3-colcon-common-extensions python3-yaml liburdfdom-tools unzip
```

## 2. Extract and build

Save `warehouse_amr_jazzy.zip` into Ubuntu's `~/Downloads` folder. This archive
contains one top-level `warehouse_amr` folder. It does not replace your existing
`warehouse_robot` tutorial package.

```bash
mkdir -p ~/warehouse_ws/src
unzip ~/Downloads/warehouse_amr_jazzy.zip -d ~/warehouse_ws/src
cd ~/warehouse_ws
source /opt/ros/jazzy/setup.bash
colcon build --symlink-install --packages-select warehouse_amr
```

## 3. Validate on Ubuntu, then launch

In a new terminal:

```bash
source /opt/ros/jazzy/setup.bash
source ~/warehouse_ws/install/setup.bash
check_urdf ~/warehouse_ws/src/warehouse_amr/urdf/warehouse_amr.urdf
gz sdf -k ~/warehouse_ws/src/warehouse_amr/urdf/warehouse_amr.urdf
ros2 launch warehouse_amr sim.launch.py
```

The launch sets `GZ_PARTITION=warehouse_custom_amr` for its Gazebo-related
processes, `QT_QPA_PLATFORM=xcb`, and software rendering by default. It uses the
graphics workaround that worked on your VMware VM. Do not start a separate
parameter_bridge or joint_state_publisher: the package already provides the
bridge, and joint states come from Gazebo's actual wheel joints.

Expect Gazebo to show a dark navy/silver AMR with orange accents in a warehouse.
RViz should show the robot, green laser points from surrounding surfaces, and a
live image in the Front camera panel. It may take time to start in a software-
rendered VM. If a command fails, keep its output and fix it before proceeding.

On a machine with working accelerated OpenGL:

```bash
ros2 launch warehouse_amr sim.launch.py software_rendering:=0
```

To diagnose Gazebo without opening RViz:

```bash
ros2 launch warehouse_amr sim.launch.py rviz:=false
```

## 4. Verify camera, laser and TF

Leave the simulator running and open a second terminal:

```bash
source /opt/ros/jazzy/setup.bash
source ~/warehouse_ws/install/setup.bash
ros2 run warehouse_amr verify_runtime.py
```

The script waits up to 30 wall-seconds. It must print PASS for the laser, image,
camera calibration, odometry, both wheel joints, simulation clock and all five
TF paths. A failure is reported as FAIL and returns a nonzero exit status.
This checks message contents, not just topic existence. It does not move the
robot or claim that visual rendering is correct.

Manually confirm in RViz:

1. Fixed Frame is `odom`.
2. Warehouse AMR display has Status OK and shows both wheels and sensors.
3. 360 degree LiDAR display has Status OK and shows points around the robot.
4. Front camera panel displays the warehouse view. If the panel is hidden,
   select Panels -> Front camera, or add an Image display with
   `/camera/image_raw` and Best Effort reliability.
5. After the movement test, the robot and scan update and the image viewpoint
   changes. Turning should keep stationary obstacle points approximately fixed
   in odom; a small mismatch from simulated wheel slip is possible.

The sensor frame tree is `odom -> base_footprint -> base_link`, then
`lidar_link` and `camera_link -> camera_optical_frame`. Wheels are children of
base_link. Camera optical axes are +Z forward, +X right and +Y down.

## 5. Move and stop

Use a third terminal with ROS sourced:

```bash
ros2 topic pub --rate 10 /cmd_vel geometry_msgs/msg/Twist '{linear: {x: 0.15}, angular: {z: 0.0}}'
```

Run for a few seconds, then Ctrl+C. The watchdog requests zero speed within
0.5 wall-seconds; the drive then decelerates in simulation. For turning:

```bash
ros2 topic pub --rate 10 /cmd_vel geometry_msgs/msg/Twist '{linear: {x: 0.0}, angular: {z: 0.3}}'
```

Ctrl+C stops the command stream. You can also explicitly send zero:

```bash
ros2 topic pub --once /cmd_vel geometry_msgs/msg/Twist '{linear: {x: 0.0}, angular: {z: 0.0}}'
```

This version has no obstacle avoidance; keep the first test short and in the
clear aisle. Its watchdog limits forward speed to 0.5 m/s, reverse to 0.3 m/s,
and turning to 1 rad/s.

## Sensor specifications (simulation configuration)

| Sensor | Settings | ROS topic |
|---|---|---|
| 2D LiDAR | 360 samples, 360 degrees, 0.12–12 m, 10 Hz simulated time | `/scan` |
| RGB camera | 640 x 360, 80 degree horizontal field of view, 5 Hz simulated time | `/camera/image_raw` |
| Camera calibration | Matching pinhole intrinsics | `/camera/camera_info` |
| Wheel odometry | 30 Hz simulated time | `/odom` |

LiDAR noise has 5 mm standard deviation; camera uses Gaussian pixel noise.
These are illustrative settings, not measurements of a particular sensor.
Software rendering may run slower than real time, so wall-clock topic rates may
be lower than configured simulation rates. This is a functional simulator, not
photorealistic sensor validation.

## Troubleshooting

- **Old robot/world appears:** close old Gazebo sessions and their launching
  terminals; this package uses a separate partition to isolate its scene.
- **Camera/laser FAIL:** inspect the launch terminal for sensor/render errors.
  Do not switch to Ogre 1: this package's GPU LiDAR is configured for Ogre 2.
- **Gazebo data exists but ROS does not:** inspect bridge messages and run
  `ros2 topic list`. For Gazebo transport inspection in another terminal, first
  run `export GZ_PARTITION=warehouse_custom_amr`, then `gz topic -l`.
- **Robot spawns slowly:** the spawn process waits for Gazebo world services;
  rendering startup may take longer in VMware. Send its logs if spawning fails.
- **TF or robot model errors:** ensure robot_state_publisher is running and
  `/joint_states` contains both wheel names. The verifier reports missing paths.
- **Very slow display:** first try `rviz:=false`, then launch RViz separately
  with the installed configuration when ready. Camera and LiDAR rendering can
  be expensive on the CPU; a working GPU offers much better performance.
